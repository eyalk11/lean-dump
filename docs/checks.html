ABOUT THE LEAN CHECKS

Read the proof status.

The Lean comparison page places each Blueprint statement beside its formal declaration. Its checks help you inspect what was formalized, what the proof depends on, and whether the saved audit still matches the source.

Four questions, four different checks

01 / FRESHNESS

Does the audit match this source?

Source hashes cover Lean files, the audit code, toolchain and dependency lockfile. Changed inputs make the audit stale; a historical report without hashes has unknown freshness. A current report records a successful build and audit of those inputs.

02 / AXIOMS

What does the proof ultimately rely on?

Lean’s axiom collection follows dependencies transitively, including dependencies of dependencies. It detects sorryAx and project axioms even when they come from another lemma. The usual Lean axioms propext, Classical.choice and Quot.sound are allowed.

03 / HYPOTHESES

Under which assumptions is it true?

Expandable details show proposition hypotheses and instances from the elaborated type, including unnamed arrows, implicit assumptions and section variables. The full type is available too. The existing conditional-status check separately flags names beginning CONJ_, UNPROVED or EXT_.

04 / CONSISTENCY

Do the documented dependencies agree?

The Blueprint’s dependency paths are compared with compiled type and proof references among mapped nodes. Audited project helpers are followed; compiler-generated helpers are expanded. External library internals are not expanded. Differences are prompts for review, since two proofs can use different arguments.

Check the evidence’s status first. Generating or opening this page does not run Lean. Missing or stale audit data leaves the new hypothesis and consistency checks unchecked. A dependency match does not establish that the manuscript and Lean statements have identical meaning.

When a warning appears

The banners below are illustrative examples, not live findings about this proof. The comparison page reports its own status.

EXAMPLE · historical report

Audit freshness: unknown

The saved report has no verifiable source hashes. “Unknown” does not mean the proof is wrong; it means the report cannot certify this version. Generate a new source-bound audit.

EXAMPLE · changed source

Audit freshness: stale — sources or configuration changed

A proof, dependency pin, toolchain or audit input changed after the audit. Even a declaration whose name stayed the same needs a new check.

EXAMPLE · missing audit

NOT CHECKED: the axiom footprint is absent

There is no saved dependency evidence. Missing evidence must not be read as “no unproved dependencies.”

EXAMPLE · inherited proof hole

CONDITIONAL: Proof depends on sorryAx

The proof reaches an admitted step, possibly several lemmas away. It cannot be presented as an unconditional result. An explicitly named project axiom or unproved hypothesis is reported similarly, with its name.

EXAMPLE · missing formal counterpart

ERROR: Lean declaration not found: Example.missingLemma

A Blueprint node points to a declaration the source extractor cannot find. Check the mapping, spelling and source coverage; a green Blueprint marker alone does not fix the missing counterpart.

EXAMPLE · dependency discrepancy

Dependency difference — Lean reaches lem:helper without a Blueprint dependency path

An amber badge and an expanded notice mark each affected statement. Inspect the two proofs. The Blueprint may have omitted a dependency, or Lean may use a different argument. The reverse discrepancy—a documented dependency absent from the compiled closure—is also reported.

EXAMPLE · incomplete Blueprint metadata

INCOMPLETE: proof has no \leanok marker

The Blueprint has not marked the proof as formalized. A Lean proof may exist, but the documentation must be checked before adding the marker.

The proof summary

“The final theorem is fully proven from Lean’s standard axioms” appears in the audit box only when the current audit covers the final theorem, it has no nonstandard axiom or flagged unproved hypothesis, and its Blueprint statement and proof are marked complete. “Sorry-free” includes the proof’s transitive dependencies. Both claims concern the final theorem, not the entire repository. Ordinary mathematical hypotheses still apply.

When a theorem names a proposition

A signature such as theorem main_bound : UNPROVED_main_bound uses a named proposition as its statement. The comparison page shows that proposition’s source in an expanded Statement definition block above the proof, when the current compiled audit resolves it. The name alone does not determine proof status.

The Full elaborated type inspector unfolds named statement definitions through Lean, showing their quantifiers and conclusion. The source definition remains separately visible in the Statement definition block.

An ordinary hypothesis is not a warning

h : n ≥ 2 describes the theorem’s scope. It does not mean that a supporting theorem remains unproved.

Read every displayed assumption in context. A clean axiom audit can accompany a conditional theorem. Conversely, a theorem with no explicit assumptions can still inherit an axiom or sorry from its proof dependencies.

What about the graph colors and #print axioms?

The graphical Blueprint reads manually supplied \leanok markers. Its green colors report those markers; the graph itself does not execute Lean. The comparison page adds the saved dependency audit and the checks described above.

#print axioms theoremName asks Lean for that declaration’s transitive axiom dependencies. An old output quoted in a comment is historical evidence, and a command appearing in source is only an instruction to run it. Trailing diagnostic commands are omitted from displayed theorem snippets; they remain in the Lean source.

Mathematical review still needs to compare quantifiers, assumptions, constants, normalization and conclusions against the manuscript. These checks make that review easier; they do not replace it.
